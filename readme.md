Валидатор должен:
- Для required_tags: как раньше – ошибка при отсутствии.
- Для conditional_required_tags: проверить условие (используя значения других тегов), и если условие истинно, то тег должен присутствовать и быть валидным.
- Для recommended_tags и opt_in_tags: если тег присутствует, проверить его тип и значения; если отсутствует – не ошибка.
Для простоты условия будем парсить вручную: поддерживаем операции >=, <=, ==, !=, AND, OR и ссылки на другие теги. Можно использовать eval с осторожностью, но для надёжности лучше написать простой парсер. Однако для демонстрации мы можем использовать простую проверку на основе словаря условий (например, {"tag": "http.response.status_code", "operator": ">=", "value": 400}). Упростим: будем проверять наличие тега и его значение

Мы должны расширить конфигурацию правил, чтобы она поддерживала три категории атрибутов: Conditionally Required (условно обязательные), Recommended (рекомендуемые) и Opt-In (опциональные, требующие явного согласия).

В текущей схеме у нас есть только required_tags (обязательные) и tag_types / value_constraints. Теперь нужно добавить секции:

conditional_required_tags – список атрибутов, которые обязательны при определённых условиях (например, наличие статуса 4xx/5xx требует error.type).

recommended_tags – рекомендуется, но не обязательно; если присутствуют, проверяем типы/значения, но отсутствие не ошибка.

opt_in_tags – аналогично recommended, но могут требовать дополнительной настройки; отсутствие не ошибка.
